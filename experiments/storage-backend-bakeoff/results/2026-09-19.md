# Results: 2026-09-19

## Environment

```text
Node.js v22.16.0
Git 2.47.3
Linux x86_64
ephemeral local filesystem
```

SQLite used WAL mode and `synchronous=FULL`. Each backend committed exactly one durable fact per authority transition.

The generated workload cycles through obligation, claim, execution-authority, effect-reservation, and receipt-shaped JSON payloads. Every run verified identical canonical replay digests across current Git replay, batched Git replay, and SQLite replay.

## Performance

| Facts | Git write facts/s | SQLite write facts/s | Git current replay | Git batched replay | SQLite replay |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 18.22 | 11,936 | 1,044 ms | 35.6 ms | 0.410 ms |
| 25 | 14.52 | 3,560 | 2,431 ms | 64.0 ms | 0.345 ms |
| 50 | 16.55 | 37,519 | 4,521 ms | 79.5 ms | 0.476 ms |
| 100 | 15.42 | 34,863 | 9,366 ms | 130.5 ms | 0.657 ms |
| 200 | 15.97 | 29,721 | 18,076 ms | 139.9 ms | 1.178 ms |

The SQLite write advantage varied from roughly 245x to 2,267x in this environment. Those ratios are **not portable benchmark constants**. The stable observation is that the Git write rate remained near 15-18 fact commits/s as the workload grew, while SQLite was nowhere near the same bottleneck.

Batched `cat-file` reduced Git replay at 200 facts from 18.1 s to 140 ms. That is important: much of the current read cost is an adapter problem and should be fixed independently even if Git becomes an export backend.

## Storage

After `git gc --prune=now`:

| Facts | Packed Git | SQLite |
| ---: | ---: | ---: |
| 10 | 34,329 B | 24,576 B |
| 25 | 41,790 B | 28,672 B |
| 50 | 54,305 B | 40,960 B |
| 100 | 79,411 B | 73,728 B |
| 200 | 129,399 B | 135,168 B |

Storage size did **not** produce a meaningful winner at this scale. By 200 facts the packed Git repository was slightly smaller than the SQLite file. Disk footprint is therefore not the architectural reason to move the hot path.

## CAS check

Two contenders attempted to advance from the same expected authority head.

```text
Git:    first=true, second=false, winners=1
SQLite: first=true, second=false, winners=1, rows=1
```

The losing SQLite transaction rolled back completely.

## Crash/reopen check

Both writers were killed with `SIGKILL` immediately after reporting the 20th committed fact.

```text
Git
  reachable facts: 20
  fsck:             clean

SQLite
  integrity_check:  ok
  authority seq:    20
  fact rows:        20
  broken parents:   0
```

SQLite therefore preserved the same property relevant to this experiment: the authority names a complete committed prefix, and reconstruction after process death does not require worker-local state.

## Interpretation

Three different issues separate cleanly:

1. **Current Git replay is unnecessarily expensive.** Batched object access improves it by orders of magnitude and is worth doing even before any storage migration.
2. **Git per-fact writes remain the hot-path problem.** Each authority transition requires multiple Git object/ref operations. The benchmark does not show a comparable bottleneck in the append-only SQLite transaction.
3. **The database did not need mutable lifecycle truth to win.** The SQLite comparator kept immutable facts, explicit parent/head identity, exact CAS, replay equivalence, and crash-safe committed prefixes.

This experiment therefore supports introducing a storage boundary and implementing an append-only database-backed fact store while retaining Git as an independently reconstructible export/reference format.

It does **not** yet prove that SQLite is the final production database. PostgreSQL, multi-process contention, remote durability, replication, backup/restore, and production-scale history sizes remain separate questions.
